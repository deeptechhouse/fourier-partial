The stack, top to bottom

Five layers. Dependencies point inward only — the domain at the bottom imports nothing from the project, and everything else depends on it. Click a layer to open it.

The arrangement is deliberate and it is what makes the dependency list short. Because every replaceable concern sits behind a typing.Protocol in backend/core/interfaces.py, swapping the audio decoder or the MIDI writer means writing one class — not threading a new library through the codebase. Libraries stay at the edges.

What we wrote against what we borrowed

Installed size, per package. Two libraries account for most of the weight, and it is worth knowing which.

numpy and scipy are 193 MB of the 248 MB. Everything else together — the web server, the schema validation, the MIDI writer, the audio codec bindings — is under 12 MB. If the install size ever needs to come down, there is exactly one conversation to have, and it is about the array library.

For scale, the code in this repository is about 13,500 lines: 5,900 of Python backend, 5,300 of front end, and 2,400 of tests.

The one thing worth knowing

certifi is MPL-2.0 — the only non-BSD/MIT/Apache licence anywhere in the tree, and the only weak-copyleft one. It arrives through httpx, which arrives through the test client.

It is development-only and never ships, so it does not reach a user. Even if it did, MPL-2.0 is file-level copyleft: it would require publishing changes to certifi's own files, and we make none. This is a footnote, not a problem — but a bill of materials that quietly omitted the one unusual licence would not be worth reading.

Attribution obligations are real but light: BSD and MIT both require the copyright notice and licence text to travel with binary distributions. For a source project run from a checkout, installing from requirements.txt puts each package's licence in site-packages alongside it, which satisfies this. Packaging it into a distributable app would mean collecting those notices into the bundle.

The front end has no dependencies

0

No framework. No bundler. No node_modules, no package.json, no build step. 5,300 lines of plain ES modules that the browser loads directly, exactly as written.

Everything it needs is already in the browser:

This is not asceticism. The front end's hard problem is sample-accurate playback of many tracks at once, and the Web Audio API solves it natively — every source scheduled at one shared AudioContext timestamp starts on exactly the same sample. A framework would not have helped with that, and would have added a build step between the source and the thing that runs.

The practical payoff: you can open frontend/js/app.js, change a line, and reload. There is no compile, no watch process, and no source map standing between what you wrote and what executes.

Why an AppleScript applet

It began as a shell script in a bundle, which was simpler and wrong. macOS will not run a bundle's executable again while that bundle is already running — it sends the running instance a reopen event, and a shell script has no way to receive one. So the second click did nothing at all: no window, no error. An applet receives the event. The logic still lives in shell, in scripts/fp_launch.sh; the applet is only the event plumbing.

The icon is generated by a Python script that writes the PNG itself with zlib and struct, because Pillow is not a dependency and adding an imaging library to draw one icon would be a poor trade.

What we deliberately did not use

A dependency list is only half the story. These are the things that were considered and rejected, with the reasons.

Not usedThe obvious case for itWhy not
librosa The standard Python audio-analysis library. Resampling, f0 estimation, STFT helpers. Removed after being specified. It was wanted for two things: scipy.signal.resample_poly covers the first and the grouper does its own harmonic search for the second. Dropping it removes the numba/llvmlite chain, which has no prebuilt wheels for macOS 12 on Intel and compiles from source for hours.
React / Vue / Svelte 5,300 lines of front end is not trivial. The hard part is audio scheduling, which no framework helps with. A framework would add a build step between source and runtime for state management this app barely needs.
A bundler Standard practice. ES modules load natively. Three files, no transpilation target older than the browsers Web Audio requires anyway.
A database Analyses have state. That state is deliberately ephemeral — uploaded audio is user data with no reason to persist. An in-memory store with TTL expiry is the correct shape, and it sits behind a JobStore protocol if Redis is ever needed.
Docker Reproducibility. The target is a double-clickable Mac app. A container would put a VM between the user and their audio files for no gain.
Pillow Generating the app icon. One icon does not justify an imaging library. The PNG is written directly with zlib and struct.
An FFT library (pyFFTW, etc.) Speed. numpy.fft is fast enough: a ten-minute analysis takes about 50 seconds, and the transform is not the bottleneck — rendering is.

Language, tooling, reproducing it

Pinned exactly

Python 3.13.12, recorded in .python-version. Every dependency is pinned to an exact version — no floating ranges, no ~=. Each was verified to exist on PyPI before being added, which is the cheap defence against slopsquatting: a plausible-sounding package name that an attacker has registered because a generated requirements file invented it.

Honest note

black, ruff, mypy, pre-commit and detect-secrets are declared in requirements-dev.txt and enforced in CI, but are not currently installed in this working environment. The test tooling is. If you are reading this expecting ruff check to run locally, install the dev requirements first.

Standard library, doing a lot of the work

The backend uses 18 standard-library modules and adds nothing to get them: threading and asyncio for the job model, dataclasses and enum for the domain types, pathlib, logging, math, socket for port selection, uuid, io, tempfile, shutil, bisect, collections, contextlib, time, typing and __future__.

Starting from nothing

On a fresh machine — including moving from Intel to Apple Silicon, where the compiled packages must be reinstalled — the whole setup is one command:

./setup.sh

It finds a suitable Python, rebuilds the virtual environment, installs with --only-binary=:all: so a surprise source build fails loudly instead of running for an hour, and smoke-tests that the backend imports.
